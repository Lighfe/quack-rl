# Self-play training

Goal: train a policy against copies of itself, with `PolicyBot` (issue #70) as the opponent. This
spec decides how. It writes no code. The loop is issue #76.

## 1. Opponent source

Decision: a pool of snapshots, not one fixed snapshot. The opponent of an episode is drawn from the
pool: the newest snapshot with probability 0.5, an older one (uniform) with 0.3, and `random`
with 0.2.

Snapshots are the files `checkpoints/step_<n>.zip` of the run folder (`RunFolder.checkpoint`
already writes them). The pool is the list of those files; a `PolicyBot.from_run`-like loader
builds a bot from one file. Snapshots stay in the run folder, so a run is reproducible and the
older snapshots can be evaluated later.

Why: one fixed snapshot is easy to overfit to (the learner finds one exploit). A pool costs only
disk space, and the older snapshots are also the test set for question 4. The `random` share keeps
the basic skill.

## 2. Update rule

Decision: every N = 50,000 training steps (decisions of the learner) a checkpoint is saved and
added to the pool. The opponent is redrawn at every episode reset. The newest snapshot is the one
from the last update, so the learner always meets an opponent at most N steps behind.

Why: a short N makes the target move too fast for PPO to follow; a long N wastes steps on an
opponent that is already beaten. 50,000 is a first guess, to be tuned after one run: if the win
rate against the newest snapshot stays above 0.8 at the next update, N is too long.

## 3. Seat and environment

Decision: `QuackEnv` with a `PolicyBot` opponent, and the seat `random` (p1 or p2 per episode).

Why: `QuackEnv` is the single-agent interface that MaskablePPO needs, and the opponent already
plugs in (`opponent=`). `QuackParallelEnv` (both seats act) would need a multi-agent trainer; with
a frozen opponent there is no gain. A random seat makes the policy play both sides; the game is
not symmetric (p1 acts first in ties), and a fixed seat would learn one side only.

## 4. What is measured

At every update, with `evaluate` at fixed seeds (`seed=0`, 500 games, the seat alternates as
`evaluate` does):

- win rate against `random`, and against the heuristic bots (the same set as the baseline
  evaluations of `train`: `random` and the `draw..` bots from the tournament), as the absolute
  strength;
- win rate against each older snapshot of the pool, as the check for cycling and progress: the
  newest snapshot should beat the older ones;
- the win rate against the newest snapshot of the previous update (should stay above 0.5).

The numbers go to `eval.json` / `metrics.csv` of the run folder in the form the notebook already
reads.

## 5. Risks

- Cycling: the policy forgets how to beat older opponents and the win rate against a snapshot goes
  up and down. Counter: the pool and the check against older snapshots (question 4). If it
  appears, raise the share of older snapshots.
- Cost of the time per step: every opponent decision runs a policy on the CPU (observation,
  `vectorize`, a forward pass), so a step is slower than with `RandomBot`. Estimate it before the
  first run (steps per second with a `PolicyBot` against `RandomBot`) and set the number of steps
  from that.
- Overfitting to itself: the policy may beat its own snapshots and lose to `random` or a heuristic
  bot. Counter: the `random` share in the pool and the fixed evaluations against the heuristic
  bots.
- Memory: a pool of loaded models costs RAM. Counter: load a snapshot only when it is drawn, keep
  at most a few loaded.
